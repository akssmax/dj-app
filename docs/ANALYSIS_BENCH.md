# Analysis accuracy bench

Run with `pnpm bench:analysis` (about 30 seconds). It decodes and analyzes in Node, using the same `analyzeAudio()` the browser worker runs.

**Sets**
- **Synthetic (12 tracks):** generated by `scripts/bench/synth.ts` with exact answers for tempo, every beat and downbeat, key and section changes. It covers 92–174 BPM, major and minor keys, off-beat lead-ins before the first downbeat, and masters tuned ±30–35 cents. It's easier than real music (clean drums, plain chord changes), so treat it as a regression floor, not proof.
- **CC tracks (5):** the bundled Kevin MacLeod tracks, scored on their published BPM only.
- **GiantSteps (optional):** set `BENCH_AUDIO_DIR` to a folder laid out as `audio/*.mp3`, `annotations/tempo/*.bpm` and `annotations/key/*.key`. The previews are copyrighted, so they are never committed. **This is the real-music check still to run.**

**Metrics**
- **Tempo:** within ±4%; "incl. octave" also accepts ×2, ×½, ×3 and ×⅓.
- **Beat and downbeat F:** F-measure at ±70 ms.
- **Key:** MIREX weighted score: same key 1, a fifth apart 0.5, relative 0.3, parallel 0.2.
- **Section F:** arrangement changes within ±1 bar.

### What changed in phase 2
- **Beat phase:** a comb over the whole track's onset envelope (kick band weighted) replaces "the first detected beat". The old grid usually sat on the off-beat hats, half a beat out.
- **Tempo:** refined to ±1% around the rough estimate, preferring whole BPMs. A doubled tempo is halved when kicks land only on every other beat.
- **Downbeat:** the beat with the strongest kick accents and the most chord changes.
- **Key:** tuning measured from spectral peaks, peak-only chroma over the whole track, and the relative major or minor chosen from the chord and bass note that open each 4-bar phrase. There is also a key per long section (`keySections`).
- **Sections:** novelty peaks at two scales (4 and 2 bars). The phrase phase comes from those peaks, and a change snaps to a 4-bar line only within one bar.

The remaining section miss is a breakdown going into a 4-bar build that keeps the same pads; stems (phase 4) should resolve it.

### Phase 3: beat-tracking model
- **Beat This!** (small, 10 MB, MIT) runs in the analysis worker through `onnxruntime-web`. Its beats and downbeats are fitted to a grid by a progressive least-squares fit that tolerates missed and extra beats. If the model can't hold one tempo while the signal-processing grid fits the onsets well, the signal-processing grid wins (it does for Club Diver).
- **ONNX export quirk:** the published exports go silent after about frame 285 (~5.7 s), so the model runs in overlapping 280-frame windows, not the upstream 1500. Within a window its output matches the expected beat count.
- **Results:** on these sets the model ties signal processing, and gives the published tempo on all five Creative Commons tracks. Its advantage should show on real music with weak or live drums, which only the GiantSteps run will measure. The grid records `method: "model" | "dsp"`.
- **Setting:** Settings → Storage → AI beat tracking turns the model off.

### Phase 4: stems (not in the bench)
- **Check:** separating a 20-second clip with htdemucs (MIT; 126 MB browser export by monteslu, MIT) and summing the four stems reproduces the mix at 27 dB SNR. The Demucs STFT and inverse STFT round-trip at about 165 dB away from segment edges.
- **Speed:**
  - CPU, single-threaded WebAssembly: about 0.7× real time.
  - Desktop GPU (WebGPU): a 2:26 track in about 55 s, plus about 11 s of Opus encoding.
- **Storage:** stems are kept as Opus at 80 kbit/s per channel. Opus encoder delay is measured by decoding once and cross-correlating, and stored stems line up with the original at lag 0.
